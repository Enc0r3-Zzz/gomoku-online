# 五子棋在线对战项目 · 可行性评估

> 依据：《Java语言及网络编程》2026-2027 课程报告说明（G:\Data\Downloads\Java语言及网络编程课程报告说明.docx）
> 评估日期：2026-11-04　｜　技术约束：Spring Boot 3.x + MySQL 8.x + Spring Data JPA + Java 17

## 0. 结论

**整体可行，工作量中等偏上（MVP 约 9–12 人日，含报告约 12–15 人日）。**

最大风险不在技术栈，而在需求内部的一组冲突：

> 第 3 条「天梯排位」要求服务端可信裁决，第 6 条「P2P 直连」要求对局数据不经过服务端——两者不可同时严格成立。

浏览器端真 P2P 只能走 WebRTC DataChannel，且必须有信令服务器与 STUN/TURN；NAT 穿透在校园网不保证成功，排位结果也无法被服务端验证（可刷分、可伪造胜负）。五子棋是回合制棋类，P2P 的低延迟收益几乎为零，却引入穿透、作弊、重连三大问题。

**建议**：把「P2P」定义为「对局双方会话直连、动作仅在两名玩家间同步」，由服务端做权威中继与胜负裁决；如老师硬性要求物理直连，再把 WebRTC 做成「休闲房」演示模式，排位房仍走服务端。这一取舍本身就是报告「方案论证」章节最好的素材。

## 2. 六项需求逐条评估

| # | 需求 | 可行性 | 关键技术 | 主要风险 |
| --- | --- | --- | --- | --- |
| 1 | 注册与登录（安全） | ✅ 高 | Spring Security 6、BCrypt、会话/JWT、参数校验、登录限流 | 细节多，容易「能登录但不安全」；token 存储方式选错会引入 XSS 面 |
| 2 | 对局内聊天栏 | ✅ 高 | 复用同一 WebSocket 连接、消息落库、频率/长度限制、转义 | 低；注意只广播给本房间，不做全局广播 |
| 3 | 天梯排位 | ✅ 高 | ELO（或 Glicko-2）、事务 + 乐观锁、MySQL 8 窗口函数排名 | 并发更新评分；刷分/小号；P2P 模式下结果不可信 |
| 4 | 匹配 + 查看排名 | ✅ 高 | 内存匹配队列 + 定时放宽分段、断线重连、榜单查询 | 并发匹配竞态、双开重复入队、等待体验 |
| 5 | 界面简洁美观 | ✅ 高 | Canvas 15×15 棋盘、响应式布局、落子动画、最后一步标记 | 工作量集中在前端；避免过度设计拖慢主线 |
| 6 | 用户直接 P2P 连接 | ⚠️ 有条件 | WebRTC DataChannel + 信令 + STUN/TURN；或服务端中继 | **架构冲突**：NAT 穿透、无法服务端裁决、断线重连与观战困难 |

### 2.1 需求 1：注册与登录

技术路线建议：

- **认证方式**：优先「HttpOnly + Secure + SameSite=Lax 的会话 Cookie + 同源部署（前端打包进 Spring Boot static）」。比「JWT 存 localStorage」更安全（免疫 XSS 窃取），也省掉 CORS/CSRF 的额外配置复杂度；WebSocket 握手能天然复用会话。
- 若坚持前后端分离 + JWT：access token 放内存（15 min），refresh token 放 HttpOnly Cookie（7 天），并显式处理 CSRF 与 XSS。
- 密码：BCrypt（strength 12），密码 8–72 字节（BCrypt 上限），必须含字母和数字；注册时做唯一性校验与频率限制。
- 登录防爆破：按「用户名 + IP」计数，5 次失败锁定 15 分钟；可选图形验证码。
- 其他：统一异常处理（不泄露堆栈）、审计日志、敏感配置走环境变量、数据库账号最小权限。

### 2.2 需求 2：聊天

- 复用对局 WebSocket 连接，消息协议 `CHAT {text}`，服务端只转发给 room 内两人并落库。
- 限制：≤200 字、1 条/秒、敏感词过滤、前端用 `textContent` 渲染（防 XSS）。
- 表：`chat_messages(id, match_id, sender_id, content, created_at)`，按 `match_id` 建索引；断线重连后可拉取最近 N 条。

### 2.3 需求 3：天梯排位

- ELO：`E = 1/(1+10^((Rb-Ra)/400))`，`Δ = K×(S−E)`；K=32（<30 局）、16（≥30 局）、10（≥2400 分）。
- 更新放在同一事务：写 `matches`、更新双方 `users.rating`、写 `rating_history`；`users` 加 `@Version` 乐观锁防并发覆盖。
- 排名：MySQL 8 窗口函数 `RANK() OVER (ORDER BY rating DESC)` 取 Top 50；「我的排名」用 `COUNT(*) WHERE rating > me + 1`。
- 防刷：同 IP 多账号检测、最短对局时长、断线判负规则。

### 2.4 需求 4：匹配与榜单

- 单机内存队列（`ConcurrentLinkedQueue` + 定时任务），按分段 ±100 起步，每 5 秒放宽 50，30 秒仍无对手则提示。
- 入队幂等：同一 userId 重复入队直接忽略；对局中禁止再匹配。
- 榜单页：Top 50 + 我的排名 + 胜/负/平 + 段位标识。

### 2.5 需求 5：界面

- 推荐 Vue 3 + Vite（组件化、开发快）；若想突出「网络编程」而非前端，也可 Thymeleaf + 原生 JS + Canvas，依赖更少。
- 棋盘用 Canvas 绘制：木纹底、星位、坐标、悬停预览、落子缩放动画、最后一手高亮、胜利连线高亮。
- 布局：左侧棋盘，下方聊天栏；右侧/顶部对手信息、计时、认输按钮；榜单独立页面。
- 移动端适配：棋盘按视口缩放，聊天栏可折叠。

### 2.6 需求 6：P2P（重点）

三种方案对比：

| 方案 | 实现 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| A. 服务端中继（推荐） | Spring WebSocket 转发 + 权威裁决 | 跨网稳定、可排位、可重连、可回放、实现简单 | 非物理直连 | 主对局通道 |
| B. WebRTC DataChannel | 信令走 Spring WS，STUN/TURN 辅助 | 真 P2P、低延迟 | 校园网 UDP 常受限、需 TURN、无服务端裁决→排位不可信、重连/观战难 | 休闲房/演示 |
| C. Java 桌面端裸 TCP/UDP | Netty + ICE/UPnP 穿透 | 最「网络编程」 | 工作量大、演示不便、穿透仍不保证 | 不推荐 |

**推荐**：A 为主，报告里明确写「逻辑 P2P / 会话直连」的设计论证；若必须展示真 P2P，用 B 做一个「休闲房」开关，排位仍走 A。这样既满足「双方直接对战」的体验语义，又保住天梯的可信度。

## 3. 建议架构

```
Browser (Vue3 + Canvas)
   │  HTTPS / WSS（同源部署，静态资源由 Spring Boot 提供）
   ▼
Spring Boot 3.x (Java 17)
   ├─ Spring Security（认证/会话/CSRF/限流）
   ├─ WebSocket Gateway（握手鉴权、心跳、房间、协议编解码）
   ├─ Game Engine（落子校验、五连判定、计时、认输、重连快照）
   ├─ Matchmaking（内存队列 + 定时放宽）
   ├─ Rating（ELO + 事务 + 乐观锁）
   └─ Chat（房间广播 + 落库）
   ▼
MySQL 8.0（utf8mb4，InnoDB，Flyway 管理 schema）
```

技术栈：Java 17、Spring Boot 3.3+/3.4+、Spring Security 6、Spring Data JPA/Hibernate 6、MySQL 8.0、Maven 3.9、Flyway（可选）、JUnit 5 + Testcontainers（集成测试）、Vue 3 + Vite（或 Thymeleaf）。

WebSocket 协议（自定义 JSON，比 STOMP 更适合写进报告）：

| 方向 | op | 载荷 |
| --- | --- | --- |
| C→S | `QUEUE_JOIN` / `QUEUE_LEAVE` | — |
| C→S | `MOVE` | `{x, y, seq}` |
| C→S | `CHAT` | `{text}` |
| C→S | `RESIGN` / `RECONNECT` | — |
| S→C | `QUEUED` / `MATCH_FOUND` | 对手信息、执黑/执白、roomId |
| S→C | `STATE` | 全量棋盘 + 最后一手 + 轮次 + seq（重连用） |
| S→C | `MOVE_ACK` / `CHAT` / `GAME_OVER` | 结果、评分变化 |
| S→C | `ERROR` | code + message |

服务端权威：轮次、落点合法性、胜负判定、超时全部在服务端；`seq` 保证幂等与顺序；断线 60 秒内可重连恢复，超时判负。

数据表（最小集）：

- `users(id, username, password_hash, nickname, rating, wins, losses, draws, status, created_at, version)`
- `matches(id, black_id, white_id, winner_id, result, started_at, ended_at, mode)`
- `moves(id, match_id, seq, player_id, x, y, created_at)`
- `chat_messages(id, match_id, sender_id, content, created_at)`
- `rating_history(id, user_id, match_id, delta, rating_after, created_at)`

## 4. 可优化与加分点

1. **服务端权威 + 对局回放**：`moves` 表天然支持回放，报告可展示「同一份落子记录复现棋局」。
2. **断线重连**：状态快照 + seq 补齐，演示时故意断网重连，效果很好。
3. **匹配质量**：分段随等待时间放宽，避免「新手被虐」。
4. **段位体系**：青铜/白银/黄金/铂金/钻石/大师，榜单更直观。
5. **计时规则**：每步 30 秒或「10 分钟包干 + 3×30 秒读秒」，增加对局张力。
6. **聊天治理**：长度、频率、敏感词、仅房间内可见。
7. **安全测试**：SQL 注入、XSS、CSRF、越权、暴力登录，写成测试表。
8. **性能压测**：k6/JMeter 压 WebSocket，给出 200 并发下的落子延迟与榜单响应。
9. **一键启动**：Docker Compose（mysql:8.0 + app），答辩现场不折腾环境。
10. **AI 工程化痕迹**：把需求写成 `skills/gomoku-spec/SKILL.md`（可验收规格 + 测试集），记录 AI 生成→人工审核→测试回填的闭环。
11. **禁手规则**：默认无禁手（自由五子棋），禁手作为可选扩展，避免范围失控。
12. **观战/好友房**：V1.1 再做，MVP 不碰。

## 7. 验收规格（可直接作为测试集/skill）

- 注册：重复用户名拒绝；弱密码拒绝；密码库中为 BCrypt 哈希；注册接口限流。
- 登录：错误 5 次锁定 15 分钟；会话 30 分钟过期；未登录访问受保护接口返回 401。
- 对局：15×15；黑先；五连（含长连）判胜；棋盘满判和；认输立即结束；每步 30 秒超时判负。
- 匹配：同分段优先；30 秒无对手提示；对局中不可重复匹配。
- 聊天：仅房间内可见；200 字截断；1 条/秒限流；XSS 载荷原样显示为文本。
- 排位：胜负后双方评分按 ELO 变化；榜单 Top 50 正确；我的排名正确；并发对局评分不丢失。
- 重连：断线 60 秒内恢复棋盘与轮次；超时判负。
- 性能：200 并发 WebSocket 连接；落子端到端 p95 < 100 ms（局域网）；榜单查询 p95 < 30 ms。

## 8. 已确认决策（2026-11-04）

1. **P2P 非必须** → 采用服务端权威 WebSocket 中继，不做 WebRTC；报告中把 P2P 作为「方案论证」的对比项。
2. **传统 + AI 工程化** → 主线走软件工程流程；AI 部分产出 spec skill、验收测试集、prompt 记录与人工审批记录。
3. **Thymeleaf + 原生 JS** → 服务端渲染页面，无 Node 构建链；同源部署，会话 Cookie 认证，表单走 CSRF token。
4. **天梯可降级** → 首选 ELO（实现简单），用 `RatingService` 接口隔离；极端情况下退化为胜负记录/胜场榜。

详细验证方式见 [初期验证方案.md](初期验证方案.md)。
